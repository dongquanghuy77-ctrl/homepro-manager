# P0.12 PRODUCTION SURGICAL MIGRATION PLAN

**Target:** `neondb` (Production)
**Objective:** Safely deploy the RBAC and Organization Tree schema (Roles, Permissions, Departments) to Production without disrupting existing `users` or `monthly_payroll` data.

## 1. Pre-requisites & Gate Checks
- [x] P0.11-C Verified by Architect
- [x] Dry Run on Production `.env.local` passed
- [x] GitHub Architect Gate blocks unauthorized runs
- [ ] Architect explicit `GO` in `.architect/DECISION.md`

## 2. Migration Scope
The migration will **ONLY** create new tables and define their relationships.
**Tables Created:**
1. `departments`
2. `manager_departments`
3. `roles`
4. `permissions`
5. `role_permissions`

**Tables Avoided:**
- `users` (No `ALTER TABLE users` commands are issued. User role associations will rely on future surgical seeding).
- `monthly_payroll`
- `attendance_logs`

## 3. Execution Strategy (Surgical Approach)
Due to Neon serverless limits on `prepared_statement` transactions with multiple commands:
1. The script will execute each `CREATE TABLE` and `ALTER TABLE` in isolated sequential requests.
2. `CREATE TABLE IF NOT EXISTS` ensures idempotency if the script is interrupted.
3. `NOT VALID` is applied to all Foreign Key constraints linking to `users` to bypass full-table scans, preventing locks and timeout failures.

## 4. Rollback Plan
- **Condition for Rollback:** If the script throws a connection error halfway, or if subsequent API calls fail in production due to the new schema.
- **Rollback Steps:**
  1. `DROP TABLE IF EXISTS role_permissions CASCADE;`
  2. `DROP TABLE IF EXISTS manager_departments CASCADE;`
  3. `DROP TABLE IF EXISTS roles CASCADE;`
  4. `DROP TABLE IF EXISTS permissions CASCADE;`
  5. `DROP TABLE IF EXISTS departments CASCADE;`
- **Safety Guarantee:** Since no existing tables are altered and no existing columns are dropped, rolling back is purely dropping the newly created tables.

## 5. Post-Migration Steps (P0.13)
After successful schema creation:
1. Seed initial system Roles (`ADMIN`, `HR`, `DIRECTOR`, `MANAGER`, `WORKER`).
2. Seed initial Permissions (`PAYROLL_VIEW`, etc.) and their mapping (`role_permissions`).
3. Only then, cautiously update existing specific `users` to map to their respective roles.
